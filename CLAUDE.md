## Project Overview

This is an event-driven algorithmic trading system that supports both backtesting with historical data and live trading through the Alpaca API. The architecture is designed around a queue-based event system where components communicate asynchronously through event objects.

## Event-Driven Architecture

The core design pattern is an event loop that processes four event types in sequence:

1. **MarketEvent** → Generated by DataHandler when new market data arrives
2. **SignalEvent** → Generated by Strategy when trading conditions are met
3. **OrderEvent** → Generated by Portfolio in response to signals
4. **FillEvent** → Generated by ExecutionHandler when orders are executed

**Event Flow:**
```
DataHandler → MARKET → Strategy → SIGNAL → Portfolio → ORDER → ExecutionHandler → FILL → Portfolio
```

All components share a reference to a central `queue.Queue()` object. The backtest engine orchestrates this flow in `backtest.py:_run_backtest()`.

## Key Architectural Patterns

### Strategy Development
- All strategies inherit from `Strategy` (abstract base class in `strategy.py`)
- Must implement `calculate_signals(event)` which receives MarketEvent objects
- Access historical bars via `self.bars.get_latest_bar_values(symbol, 'adj_close', N=50)`
- Generate signals by creating `SignalEvent` objects and putting them on the event queue
- Example implementation: `mac.py` (Moving Average Crossover)

### Execution Handler Swap Pattern
The system uses polymorphism to swap between simulated and live execution:
- **Backtesting**: Use `SimulatedExecutionHandler` (converts orders to fills instantly, no latency)
- **Live Trading**: Use `AlpacaExecutionHandler` (submits real orders via Alpaca API, handles WebSocket updates)

Both implement the same `ExecutionHandler` interface, so strategies are environment-agnostic.

### Data Handler Swap Pattern
Similar pattern for data sources:
- **Backtesting**: Use `HistoricCSVDataHandler` (reads CSV files, simulates real-time feed)
- **Live Trading**: Use `AlpacaDataHandler` (currently skeleton implementation in `alpaca_data.py`)

## Running the System

### Backtesting
```bash
python mac.py
```

This runs a Moving Average Crossover strategy backtest. Key parameters in `mac.py`:
- `csv_dir`: Location of CSV data files (currently `./`)
- `symbol_list`: List of tickers (e.g., `['AMD']`)
- `initial_capital`: Starting portfolio value
- `start_date`: Backtest start date

Output: Prints performance stats and generates `equity.csv` with equity curve data.

### Live Trading
```bash

```


Currently configured to execute a single test order. The WebSocket connection runs in a daemon thread to receive trade updates.

### Data Download
```bash

```

Downloads historical data from Yahoo Finance using `yfinance`. Currently hardcoded to download AMD data. Outputs CSV in the format expected by `HistoricCSVDataHandler`.

## CSV Data Format

Historical data must have these columns (in this order):
```
datetime,open,close,adj_close,volume
```

The `HistoricCSVDataHandler` reads CSVs with this specific format. The filename must match the symbol (e.g., `AMD.csv` for symbol 'AMD').

## Portfolio Management

The `Portfolio` class tracks two key data structures:
- **positions**: Dictionary of symbol → quantity held
- **holdings**: Dictionary of symbol → market value, plus 'cash', 'commission', 'total'

These are updated on every bar (via `update_timeindex()`) and on every fill (via `update_fill()`). Historical snapshots are stored in `all_positions` and `all_holdings` lists for performance calculations.

### Position Sizing
Default implementation uses fixed 100-share orders (see `portfolio.py:generate_naive_order()`). Modify this method to implement custom position sizing or risk management.

### Commission Model
Default commission is 0 (see `event.py:FillEvent._calculate_commission()`). Update this method to model realistic transaction costs.

## Alpaca Integration

### AlpacaExecutionHandler
- Operates in **paper trading mode** (`paper=True`)
- Maintains WebSocket connection via `TradingStream` to receive order updates
- Tracks order states in `fill_dict` to prevent duplicate fills
- Converts 'LONG'/'SHORT' direction to Alpaca's `OrderSide.BUY`/`OrderSide.SELL`

**Important**: The WebSocket must run in a separate thread (`threading.Thread(target=execution_handler.open_connection, daemon=True)`)

### Order Types
- Market orders: `'MKT'` → `MarketOrderRequest`
- Limit orders: `'LMT'` → `LimitOrderRequest` (limit price not implemented, TODO at line 117)

## Performance Metrics

Calculated in `performance.py`:
- **Sharpe Ratio**: Annualized risk-adjusted return (default assumes 252 trading days)
- **Drawdowns**: Peak-to-trough decline using high water mark algorithm

The `periods` parameter in `create_sharpe_ratio()` must match the bar frequency:
- Daily bars: 252
- Hourly bars: 252 * 6.5
- Minute bars: 252 * 6.5 * 60

## Common Gotchas

1. **Direction vs Side**: Strategies use 'LONG'/'SHORT'/'EXIT', OrderEvents use 'BUY'/'SELL', Alpaca uses `OrderSide.BUY`/`OrderSide.SELL`. The ExecutionHandler handles conversion.

2. **CSV Index**: CSVs must have datetime as index. The `HistoricCSVDataHandler` uses `parse_dates=True` and expects the first column to be datetime.

3. **Event Queue Blocking**: In backtesting, the inner while loop (`backtest.py:93-121`) processes all events before fetching new bars. If a component doesn't put expected events on the queue, the loop may hang.

4. **AlpacaDataHandler Incomplete**: The live data handler is a skeleton. For live trading, you'll need to implement the bar update logic using Alpaca's data API or WebSocket.

5. **Order ID Tracking**: `AlpacaExecutionHandler` uses `self.order_id` to track the most recent order. This only works for sequential single orders. Concurrent orders need a more sophisticated tracking mechanism.

## Testing Strategy Changes

To test a new strategy:
1. Create a class inheriting from `Strategy`
2. Implement `calculate_signals(event)`
3. Replace `MovingAverageCrossStrategy` in the `Backtest` instantiation (see `mac.py:82`)
4. Run the backtest
5. Review `equity.csv` and printed stats

The system automatically calculates all performance metrics when `backtest.simulate_trading()` completes.
